Berkeley DB is one of the most widely deployed pieces of software ever
written.  For most of the 2000s it was underneath OpenLDAP, Postfix,
Sendmail, Subversion, Bogofilter, RPM, and a long tail of things that
needed a fast embedded key-value store and did not want to write one.
It shipped inside routers, set-top boxes, and phones.  If you ran a
Unix box in 2005 you were almost certainly running Berkeley DB without
knowing it.

Then Oracle bought Sleepycat in 2006, and over the following decade
did the two things that kill a piece of infrastructure software.
First, in 2013, they relicensed the 6.x line from the old Sleepycat
license to AGPLv3.  For a library that lived *inside* other people's
programs, AGPL was a bomb: every downstream now had to either publish
their own source under AGPL or stay on the last pre-6.x release
forever.  Debian
[chose to stay on 5.3](https://wiki.debian.org/BerkeleyDB) and then to
remove it entirely.  Everyone else quietly migrated to LMDB, SQLite,
or RocksDB.  Second, Oracle stopped meaningfully developing it.  The
public repository went dark.  The last thing that happened to Berkeley
DB in public was the license change that made people leave.

I spent years at Sleepycat.  I wrote the SQL layer that became Berkeley
DB SQL, I worked on the replication and high-availability code, and I
have opinions — mostly fond, occasionally scarred — about the codebase.
Watching it get orphaned by a license change rather than by any
technical failing bothered me enough to do something about it.

## the fork

The revived tree is [`berkeleydb/libdb`](https://github.com/berkeleydb/libdb).
It starts from **5.3.28**, the last release under the Sleepycat license —
the version Debian froze on, the version everyone who left Oracle's 6.x
line was already using.  That choice is the whole point: 5.3 is the
fork breakpoint that keeps the license permissive.  The Sleepycat
license is BSD-with-a-copyleft-clause; it lets you embed the library in
proprietary and open code alike, which is exactly the property that
made Berkeley DB ubiquitous and exactly the property AGPL destroyed.

New work in the fork carries a separate permissive license so the
whole thing stays embeddable.  The tree is explicitly **not affiliated
with or endorsed by Oracle** — it is a community revival of the last
freely-licensed release, not a continuation of Oracle's product.

I also reconstructed the full published lineage on a `historical`
branch: every release from **1.85** in 1992 through **5.1** in 2011, so
the archaeology is there for anyone who wants to read how a storage
engine evolved across two decades.  There is a surprising amount to
learn from the diffs.

## a build system from this decade

The single biggest barrier to picking up an old C library is not the
code, it is getting it to compile.  Berkeley DB's original build was a
hand-maintained tangle of `dist/` shell scripts, m4, and per-platform
`Makefile` fragments that generated the actual build.  It worked, in
the sense that it built on the platforms Sleepycat and then Oracle
cared about, and it was inscrutable everywhere else.

The revival keeps the Autoconf build as the reference — it still
produces the full feature set and all the language bindings — but the
primary build is now [Meson](https://mesonbuild.com/) plus Ninja.
Public API headers that used to be generated by opaque shell are now
generated by small, readable Python scripts from the same `.in`
templates.  There is a Nix flake that gives you a reproducible dev
shell with the whole toolchain, including the optional bits —
`liburing` for async I/O, CBMC for the model checking — so `nix
develop` gets you from a clean checkout to a working build in one
command.

CI builds the matrix that actually matters now: Linux under both GCC
and Clang, macOS under Clang, Windows under MSVC, and an aarch64
Android cross-compile.  The Windows project files, which had rotted
into referencing headers that no longer existed, are regenerated and
build clean.  None of this is glamorous.  All of it is the difference
between a library people can use and a tarball people bounce off of.

## why bother

The honest question is whether the world needs Berkeley DB back when
it has LMDB and RocksDB and SQLite.  I think the answer is yes, for two
reasons.

The first is that a great deal of deployed software still depends on
the Berkeley DB API and has no clean migration path.  Those users
deserve a maintained, permissively-licensed engine that speaks the API
they already build against, rather than being stranded on a decade-old
Oracle release with known bugs and no fixes coming.

The second is more interesting to me.  Berkeley DB's access-method
architecture — pluggable B-tree, hash, queue, and recno methods over a
shared page cache, lock manager, and write-ahead log — is genuinely
good design, and it has room to grow into a modern multicore storage
engine in a way its contemporaries mostly do not.  The
[roadmap](https://github.com/berkeleydb/libdb/blob/main/ROADMAP.md) says
the goal out loud: match or beat InnoDB and WiredTiger on throughput
*and* on scalability across large multi-socket NUMA machines.  That is
an ambitious thing to say about a codebase from the 1990s, and whether
it is achievable is the subject of a later post.  But the bones are
there, and the license is finally out of the way.

## status

The fork is at 5.3.33.  It builds on Linux, macOS, Windows, and
Android/aarch64.  It is a work in progress and I am doing that work in
the open.  The repo is at
<https://github.com/berkeleydb/libdb>; issues, patches, and war
stories from people who shipped Berkeley DB in anger are all welcome.

Two more posts follow this one: what it takes to trust a storage engine
again after a decade of neglect, and where the performance actually
stands today.
